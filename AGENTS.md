# Project implementation guidance

The requested Ponytail, Graphify, and UI UX Pro Max skills are applied as development guidance, adapted to this Python/Textual project rather than added as runtime dependencies: keep changes lean, make module relationships easy to trace, and prioritize responsive, accessible keyboard-first terminal UX. A generated graph is deferred while the package remains small and explicit.

- Keep the implementation no larger than the current milestone requires; reuse the standard library before adding dependencies.
- Read the existing code path before editing, and add focused tests for branching, traversal, cancellation, and data-loss-sensitive behavior.
- Keep filesystem logic independent of Textual. UI handlers must delegate blocking work to `ScanService`.
- Represent unknown sizes as `None`; never turn inaccessible or incomplete scans into a successful zero-byte result.
- Do not follow symlinks or Windows reparse points by default. Keep worker concurrency bounded and cancellation cooperative.
- Never drop an entry silently: a skipped entry carries a `SkipReason` in `skipped_details`, and an unreadable path stays an error. Skips keep a scan complete; errors make it partial. Do not fold one into the other.
- Keep Python and Rust engines behaviourally identical. `tests/test_engine_contract.py` defines the shared tuple contract and compares the engines when the extension is importable; `tests/test_rust_source.py` guards the build (no unstable `windows_by_handle` APIs, PyO3 signatures match `FileSystemScanner`).
- The Rust crate must build on stable Rust (MSRV in `Cargo.toml`, currently 1.80) with only stable APIs.
- The SQLite cache is a disposable accelerator, never a source of truth: keep it out of `core/` and `ui/`, never let its failures reach the user as errors, and remember that deleting the file must only cost a rescan.
- Cache rules that must not regress: listings and recursive sizes live in separate tables with separate validation; a miss always means "scan it"; expired rows are invalidated, not refreshed silently.
- Cached data must always carry its own truth: `is_complete` and `errors` travel with the row. A *partial* recursive size may be cached (it is the expensive case) but only together with its error list, and it must come back with `is_complete=False` and be labelled `cached partial` in the UI. A cancelled walk is never cached. Directory *listings* stay strict - a partial listing would silently hide children - and an unreadable folder is never cached as a complete empty scan.
- A cached partial total is a lower bound, not a size. `scan_service.display_size()` holds the only rule for turning it into a displayed number; do not re-derive it elsewhere.
- Keep cache policy in `cache/validator.py` (pure) and `cache/cache_service.py` (orchestration); `services/scan_service.py` only decides the order of operations. Add a test for every new invalidation path, since a wrong hit is silent data corruption from the user's point of view.
- Benchmark before claiming a performance win (`scripts/benchmark_cache.py`, `scripts/benchmark_scanner.py`). State the machine, filesystem and cache state, and say plainly when caching does not help.
- The Analyzer (`analyzer/`) is analysis only: it must walk with `FileSystemScanner` and reuse `CacheService`, never add a second scanning engine or its own SQLite access. Keep it free of Textual imports (a test enforces this) so M4 Search and M5 Cleanup can reuse `AnalysisSnapshot`.
- Analysis invariants: recursive folder totals are never summed into a grand total (files only); unknown sizes stay `None` and export as blank, never `0`; the scan status (`complete`/`partial`/`cancelled`/`failed`) travels with every snapshot and every CSV; limiting the walk marks the result partial with an explanation rather than truncating silently.
- Sizing cost rule: enumerate each directory exactly once and derive every folder's recursive total from that walk (bottom-up subtree sums in `AnalyzerService._subtree_totals`). Never call `scanner.calculate_size()` per folder during a walk, and never add a "fill the gaps by scanning" pass - both are O(folders x tree) and turned a 16k-folder analysis into ~15 s. `tests/test_analyzer.py::test_analysis_never_rescans_subtrees` fails if this regresses.
- Cache-use rule for the Analyzer: a warm run must not touch the disk for folders whose cached listing is still valid. Read listings in batches (`CacheService.cached_listings`), enumerate only the misses, and write back only what changed (`_store_totals(..., unchanged=...)`); rewriting unchanged rows cost more than the walk it was meant to save. Report the hit count (`AnalysisSnapshot.cached_directories`) so the user can see the cache working instead of taking it on faith.
- Visual layer (`analyzer/visuals.py`) is stdlib-only text rendering with no Textual imports: bars, a clockwise ring, and a squarified treemap. Chart honesty rules: draw only mutually exclusive folders (`AnalysisSnapshot.children`, never `largest_folders`, which contains ancestors), never draw an unknown size as zero, give every measured folder at least one cell, and account for anything not drawn instead of cropping silently.
- Top-N uses bounded heaps (`analyzer/aggregators.py`) with an explicit ordering rule: size descending, then path ascending, so equal sizes produce stable reports. Do not replace this with a full sort of every file.
- Design for keyboard-first use and small terminal sizes; keep labels readable and state visible.
- Explorer ordering is part of the contract (name, size, modified, type): folders stay grouped above files in every order, unknown values sort last in both directions, the active column is marked with an arrow, and a size sort re-orders rows while folder sizes are still arriving.
- For this small repository, the module tree and typed service contracts are the source of truth; avoid generated graph artifacts until the codebase is large enough to benefit.
